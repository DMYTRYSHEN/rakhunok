# Delivery: план переходу до реального трекінгу

Дата дослідження: 2026-10-07. Статус: план для погодження, не реалізована інтеграція.

Уточнення користувача від 2026-10-07: погоджено напрямок реального пілоту Нової пошти, потім Укрпошти за доступністю. Перший пріоритет — трекінг через один дозволений ключ сервісу без ключів кожного клієнта. Майбутнє створення відправлень під credentials клієнта є окремим етапом. Актуальна уніфікована модель, політики доступу та межі погодження: [база знань Delivery](DELIVERY_KNOWLEDGE_BASE.md). Live-доступ і production ще не активовані.

## 1. Що працює зараз

Демо запущене на http://127.0.0.1:5173/; бізнес-кабінет: http://127.0.0.1:5173/business.
Головна сторінка позначає дані як демонстраційні. 18 перевірок бізнес-навігації на ширинах 1440, 390 і 320 px пройшли.
Це локальна демонстрація, не зовнішній production-сервіс; доступ з іншого пристрою не налаштовано.

Наявна [специфікація](SHIPMENT_TRACKING_SERVICE_SPEC.md) залишається концепцією. Цей документ доповнює її перевіреними джерелами, не змінює її й не дозволяє інтеграції з Dashboard/Pay або платежами.

## 2. Рекомендований старт

Перший живий пілот: Нова пошта, мінімальний трекінг дозволених накладних різних клієнтів через один сервісний ключ, якщо підтверджені технічні та договірні права; поточний статус, безпечна точка отримання та час останнього успішного оновлення.
Наступний адаптер: Укрпошта за наявності дозволеного tracking-доступу. Meest Пошта, SAT, Delivery Auto, ROZETKA Delivery і Nova Post залишаються подальшою чергою за потребою клієнтів.

Не починати зі створення ТТН, виклику кур'єра, переадресації, повернення коштів або повної багатоперевізникової платформи.
Відстеження доставки кур'єром до адреси входить лише там, де вибраний API та договір його підтримують. Це не API замовлення кур'єра.

### Особливості Нової пошти з відкритого користувачем порталу

- Точка входу JSON: `https://api.novaposhta.ua/v2.0/json/`.
- `methodProperties.Documents` містить `DocumentNumber`; `Phone` дозволяє розширену інформацію. Не збирати телефон за замовчуванням, не вгадувати й не отримувати його з інших джерел.
- Опис допускає неавторизовані запити, але повідомляє про підміну даних відправника/одержувача даними телефону із запиту. Не використовувати такі поля як достовірну ідентичність; MVP показує мінімальні неперсональні дані.
- До 100 документів означає максимум пакета, не 100 запитів на хвилину.
- Поточний статус не є доказом повної історії. Якщо API дає лише snapshot, накопичувати спостережувані зміни після підключення й явно зазначати, що попередня історія недоступна.
- Перевіряти структуру відповіді, логічний `success` і помилки, не лише HTTP 200.
- API v2.0 і Nova Post v.1.0 мають різні контракти. Не переносити JWT, webhooks або методи між ними автоматично.

### Межі перевірки

Офіційні PDF Укрпошти та Delivery Auto знайдено, але текст не вдалося змістовно витягти поточними інструментами. Деталі з них залишені відкритими, а не припущеними.
Для DHL/UPS/FedEx та сервісів термінової міської доставки окремий аудит не проведено: включати після визначення реальних напрямків і договорів, не обіцяти їх у початковому покритті.
Justin не активувати без підтвердження чинної діяльності й офіційного доступу.

## 5. Етапи реалізації та вихідні критерії

### Етап 0. Доступи й технічний контракт

Отримати дозволений сервісний ключ Нової пошти, погодити права показу/кешування мінімальних статусів і трекінгу накладних різних клієнтів, отримати квоти. Контрольний набір має включати накладні щонайменше двох незалежних клієнтів; перевірка виконується тим самим ключем без їхніх окремих ключів. Якщо scope не дозволяє, явно зафіксувати обмеження, а не обходити його.
Взяти 10–20 дозволених реальних накладних у різних станах: нова, у дорозі, до отримання, вручена, повернення, кур'єрська доставка; перевірити обидві назви моделі з документації в контрольованому середовищі.
Результат: знеособлені fixtures успіху/відмов, погоджена модель, мапа доступних полів і статусів. Жодні синтетичні demo-номери не надсилати перевізнику.

### Етап 1. Один живий lookup

Серверний адаптер Нової пошти: валідація, timeout, перевірка payload, batch, cache, захист від зловживань; ключ лише на сервері, не `VITE_*`, не в браузері й не в логах.
Backend повертає номер, підтвердженого перевізника, статус, точку отримання, свіжість, джерело. Публічний запит не надає доступ до бізнес-даних або необмеженого моніторингу.
Результат: дозволена реальна ТТН показує перевірений стан; невідомий номер та відмова API не створюють фальшивий успіх.

### Етап 2. Постійне оновлення й історія

Збереження shipment/event; scheduler вибирає due jobs, lease запобігає одночасній роботі; per-provider і per-credential throttling, backoff/jitter, обробка 429/timeout, retry і dead-letter.
Частоту визначити після квот: частіше активні/очікують видачі, рідше terminal; разовий lookup має TTL і не запускає нескінченне опитування.
Мапінг статусів версіонований; technical failure окремо від delivery status; unknown не перетворювати на lost.
Результат: перезапуск не губить job, повтор не дублює події, stale видно, пізні події/повернення не відкидаються без правила.

### Етап 3. Живий бізнес-кабінет і довідники

Auth/tenant isolation, реальні list/detail/events, CSV з помилками по рядках, дедуплікація, фільтри, оновлюваний довідник усіх відділень/поштоматів із пагінацією та перевіркою повноти.
Дата синхронізації та застарілий графік видимі; pickup визначається відправленням, не найближчою картою.
Результат: дані зберігаються після перезапуску; інша організація не може читати чужі записи; лічильники відповідають реальним даним.

### Етап 4. Сповіщення та додаткові адаптери

Підтверджений email/Telegram, підписка/відписка, outbox і повтори з дедуплікацією, журнал доставок.
Для Nova Post: автентичність callback перевіряти за точним контрактом, не вигадувати HMAC; захист від replay, контрольна звірка polling. Для інших служб не називати polling webhook-інтеграцією.
Кожен наступний адаптер проходить той самий контрактний пілот; capabilities увімкнені лише для перевірених функцій.

### Етап 5. Зовнішній пілот

Погодити домен/hosting, persistent scheduler, окремі dev/prod secrets, TLS, квоти, резервні копії та відновлення, метрики джерел, alerts, privacy/retention, ротацію ключів.
Перевірити load, недоступність перевізника, cross-tenant/anonymous access, redaction, retry, припинення підписки й відновлення після збою.
Production deployment потребує окремого явного погодження. Поточне демо та цей план таким погодженням не є.

## 6. Що потрібно зробити вам

1. Перший пілот обрано: Нова пошта; Укрпошта наступна. Уточнити обсяг і допустиму свіжість мінімального трекінгу накладних різних клієнтів.
2. Підготувати один API-ключ сервісного облікового запису Нової пошти та погодити його scope. Не надсилати ключ у чат, не вставляти у портал-демо: зберегти в локальному server-only secret або secret store обраного hosting під час реалізації. Ключі кожного клієнта не є обов'язковим входом першого режиму, якщо shared access дозволений.
3. Погодити з перевізником роль агрегатора, допустимий набір даних, квоти, кешування, строк зберігання та права показу третім особам. Наявність ключа сама по собі цього не дозволяє.
4. Підготувати 10–20 накладних, які ви маєте право перевіряти, та очікувані статуси з офіційного кабінету. Передавати телефони лише якщо без них необхідний конкретний дозволений scope.
5. Назвати очікуваний масштаб: активні накладні/день, організації, потрібна затримка оновлення, частка міжнародних/кур'єрських доставок, бюджет hosting і сповіщень.
6. Для наступної черги отримати окремий tracking key Укрпошти, контракт/токен Meest; SAT і Delivery Auto підключати за наявності вантажних клієнтів. ROZETKA та Nova Post — за реальним попитом.
7. Напрямок пілоту погоджено; поточний результат — документація. Перед зовнішніми операціями визначити конкретні credentials, дозволені тестові номери та середовище. Створення/зміна реальних накладних, Dashboard/рахунки/платежі, remote migrations і production потребують окремого погодження.

### Текст запиту техпідтримці перевізника

> Ми створюємо сервіс відстеження доставки для продавців і їхніх покупців, без створення/зміни накладних. Просимо підтвердити доступ до статусів власних і делегованих/сторонніх накладних, мінімальні поля без персональних даних, допустимість показу й кешування в нашому сервісі, квоти та batch limits, рекомендовану частоту polling, доступність повної історії/довідника точок і webhook, тестові умови, ротацію ключів та вимоги до договору. Для Нової пошти також просимо уточнити TrackingDocument проти TrackingDocumentGeneral у чинному getStatusDocuments.

## 7. Оцінка та критерій «реально працює»

Орієнтир планування для одного розробника після отримання доступів: контрактна перевірка 1–3 робочі дні; захищений lookup 3–5; persistence/polling 5–8; живий кабінет/довідники 4–7; стабілізація пілоту 3–5. Загалом приблизно 3–6 тижнів для однієї служби, не обіцянка строку. Договори, hosting-рішення, auth та нові вимоги можуть подовжити роботу; решта адаптерів оцінюється після контрактних fixtures.

Готовність: реальний дозволений номер → підтверджене джерело → збережений стан → повторне автоматичне оновлення → перевірена зміна статусу → правильне відображення свіжості/відмов. Пілот лише з ручним lookup не називати постійним моніторингом; робочий UI не дорівнює живій інтеграції.

Мінімальні негативні тести: невалідний/порожній номер, чужий tenant, відкликаний ключ/401, 429, timeout, логічна помилка при HTTP 200, дубль callback/job, подія не по порядку, виправлення статусу, перезапуск scheduler, неповний довідник, витік секретів у response/logs.

Бюджет складається з hosting/runtime, scheduler/queue, БД і резервних копій, логів/моніторингу, домену, email/SMS та Google Maps за реальною тарифікацією. Генерація ключа Нової пошти описана як безкоштовна, але це не підтверджує безкоштовний необмежений агрегатор або права на перепродаж даних. Тарифи й квоти інших служб погодити окремо; до обсягів і договорів грошова оцінка була б припущенням. Контрольна формула навантаження: активні накладні × перевірки на добу / фактичний розмір пакета, плюс первинні lookup, довідники та retries; тарифний облік може відрізнятись.
