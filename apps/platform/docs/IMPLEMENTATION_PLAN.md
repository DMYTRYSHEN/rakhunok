# Rahunok Platform: план реалізації

Дата початкового плану: 2026-09-27. Статус: E1-E7 розширено та перевірено в межах локальної синтетичної моделі; актуальні можливості й обмеження наведені в розділах 16-18. Автоматизований gate E8 пройдено, ручне візуальне приймання відкрите. Це не повне виконання нормативних вимог, production readiness або підтвердження правової відповідності.
Джерела, юридичні застереження та огляд прототипу: [база знань](PLATFORM_KNOWLEDGE_BASE.md).

## 1. Рішення користувача

- Спочатку повний інтерактивний демоцикл, потім поетапне підключення реального backend.
- Перша юрисдикція: Україна. VARUS Delivery використовується як демонстраційний приклад, не підтвердження партнерства або підключення.
- Три основні кабінети: оператор, самозайнятий, адміністратор Rahunok. Доставка є першим сценарієм; також підтримуються таксі, послуги й інша діяльність.
- Обидва режими виплат: облік зовнішніх та формування/погодження батчів.
- Невідомі державні, банківські та ідентифікаційні інтеграції реалізуємо візуально з мокованими відповідями, явно позначеними як симуляція.

Користувач визначив напрям і послідовність. Деталі нижче є інженерною декомпозицією; нові суттєві обмеження/розширення погоджуються окремо.

## 2. Межі та принципи

Перша черга локальна: `apps/platform`, тести й документація. Не змінюємо Dashboard, checkout, спільні auth-процеси, історичні міграції або чинні Workers. Реальні PII, секрети, provisioning, deployment, платежі й подання не входять у дозвіл на демореалізацію.

Реальними в демо є взаємодія, валідація, переходи станів, локальний імпорт, звірка та розрахунки синтетичних даних. Мокуємо зовнішніх учасників і їхні відповіді. Не створюємо незалежні декоративні екрани: зміна операції має відображатися у виплатах, кабінеті кур'єра та нових звітах.

- Єдиний demo gateway і спільний стан; майбутній API реалізує ті самі узгоджені операції, але не довіряє клієнтській авторизації.
- Новий демопроцес не використовує live gateway з fixture fallback/default admin. Зберігаємо чинний null-client boundary.
- Режим demo визначений для всієї сесії; помилка live ніколи не перемикає модуль на моки.
- Позначки DEMO у статусах і експортованих документах. Демоключі не авторизують реальний API; державні квитанції не видаються за справжні.
- Точні грошові значення; для UAH у демо minor units, без float-арифметики для підсумків.
- Оплата покупця, винагорода кур'єра та фактична виплата є трьома пов'язаними, але різними реєстрами.
- Первинні події не перезаписуються; корекція має посилання, причину, автора й час.
- Непідтверджені ставки/форми зберігаються як demo assumptions, а не чинні українські правила.
- Поточні інші демокабінети не видаляються без окремого рішення. Legacy admin не стає автоматично адміністратором SaaS.

## 4. E1: основа демо

Критерії розділів 4-9 нижче збережені як початкова специфікація, а не поточний task list. Фактичний статус кожного модуля та докази наведені в розділі 16. Відкриті вимоги приймання відокремлені в розділі 17.

- [ ] Прочитати owning components/gateway і найближчі тести; повторно використати таблиці, drawer, pagination та стиль. Не переписувати весь застосунок наперед.
- [ ] Визначити типізовані операції нового demo gateway, результати й помилки; UI не залежить від способу зберігання.
- [ ] Підготувати синтетичні дані: VARUS Delivery, другий вигаданий оператор, щонайменше чотири кур'єри, один спільний, кілька періодів, зафіксовані контрольні суми.
- [ ] Ввести окремі demo persona/context: оператор, кур'єр, адміністратор Rahunok; бухгалтер/підписант/compliance/інтегратор як права всередині оператора.
- [ ] Навігація оператора: огляд, реєстрація, кур'єри, операції, виплати, звіти, інтеграції, команда, журнал. Для інших кабінетів лише відповідні розділи.
- [ ] Пряме відкриття екрана, назад/вперед, перемикання контексту. Не додавати landing page.
- [ ] Версійоване локальне сховище лише синтетичного стану, окремий ключ, без auth-токенів. Reset не очищує SDK-сесію або інші застосунки.
- [ ] Порожні/завантажувальні/помилкові стани, перевірка форм, відновлення пошкодженого demo storage.

Приймання: A/B не змішуються; reload зберігає зміни; reset відновлює контрольні суми; вихід із демо не виконує live signOut; жодних бізнес-записів у Supabase/банк/ДПС. Клієнтська ізоляція демо не є доказом серверної безпеки.

Перший малий slice: спільний стан двох операторів, явний demo-context та перемикання трьох кабінетів. Після focused test додати навігацію, reload і reset.

## 5. E2: реєстрація оператора

- [ ] Майстер: організація, цифрові платформи, види діяльності, представники, контакти, документи, комплектність, перегляд пакета.
- [ ] Чернетка з продовженням після reload; невідомі юридичні вимоги позначені як демонстраційні.
- [ ] Версія пакета, історія, погодження окремою демоперсоною підписанта. Зміна пакета скасовує погодження для нової версії.
- [ ] Симулятор: розгляд, уточнення, відмова, реєстрація, недоступність каналу. Повторна дія не створює дубль.
- [ ] Статус із джерелом, часом, причиною й демоквитанцією. Ручний сценарій подання/доказів; завантажений файл сам собою не є перевіреною відповіддю органу.

Приймання: нова реєстрація і цикл уточнення завершуються; порожній пакет не подається; локальне погодження не означає державну реєстрацію; усі симульовані результати мають DEMO.

## 6. E3: самозайняті, команда, докази

- [ ] Реєстр: пошук, фільтри, пагінація, профіль, відносини з оператором, стан перевірки.
- [ ] Відокремити продавця від auth-користувача; фізособа/ФОП без припущення про автоматичне звільнення ФОП від звітності.
- [ ] Резидентство/TIN, рахунок, документи, джерело й дата перевірки, запити на уточнення. Дія, BankID та IBAN ownership є окремими симуляціями.
- [ ] Команда: запрошення, прийняття/відкликання, права, деактивація. Email записується у деможурнал, не надсилається.
- [ ] Спільний кур'єр у двох операторів; введення email/РНОКПП не надає доступу без змодельованого підтвердження зв'язку.

Приймання: кур'єр бачить лише власні A/B, оператор A не бачить B; бухгалтер не змінює команду; інтегратор не погоджує звіт; відсутній/прострочений доказ створює невідповідність. Права до E9 є UI-симуляцією.

## 7. E4: інтеграції та операції

- [ ] Демоключі зі scopes, test/live статусами, ротацією/відкликанням і журналом. Live недоступний до E9.
- [ ] Інтерактивна API-консоль: JSON-приклад, редагування, запит до локального адаптера, помилки та correlation ID.
- [ ] Узгодити ресурси: seller relationship, activity/income event, customer payment, external payout, adjustment, batch, report, submission. Старий OpenAPI перевіряти по ресурсу, не вважати готовим backend.
- [ ] Справжній локальний CSV/JSON parser для синтетичних файлів: mapping, preview, помилки рядків, обмеження, результат. XLSX окремим розширенням за потреби.
- [ ] Валюта, точна сума, external ID, час події/отримання, продавець і діяльність; типізовані результати приймання та обробки.
- [ ] Ідемпотентність operator/operation scoped: той самий ключ/payload повертає попередній результат; інший payload з тим самим ключем дає конфлікт.
- [ ] Три реєстри з переходом до джерела; повернення, скасування, перепризначення й коригування окремими подіями.

Приймання: повтор імпорту не змінює сум; невідомий кур'єр, неправильна валюта, конфлікт ID відхиляються; коригування видно на пов'язаних екранах; CSV-експорт захищений від formula injection.

## 8. E5: виплати та звірка

- [ ] Зовнішні виплати: provider reference, одержувач, сума, дата, статус, джерело підтвердження.
- [ ] Батч із придатних залишків: період/кур'єри, рахунки, дублікати, preview сум, чернетка.
- [ ] Погодження іншим уповноваженим учасником, експорт інструкцій або симулятор банку; зміна складу/суми потребує нового погодження.
- [ ] Pending, часткове виконання, відмова, timeout з невідомим результатом, пізнє підтвердження. Невідомий результат потребує звірки перед повтором.
- [ ] Не включати винагороду одночасно в кілька активних батчів; retry лише підтверджено невиконаних придатних інструкцій зі стабільними ID.
- [ ] Звірка: нараховано, скориговано, зарезервовано, виплачено, залишок; неоднозначність передається на розгляд.

Приймання: створення/експорт не дає paid; повтор webhook не подвоює виплату; частковий батч зберігає успішні позиції; повтор не відправляє їх знову; історія зберігається.

## 9. E6: звітність і подання

- [ ] Оператор, період, версія demo ruleset; непідтверджені ставки не використовуються як чинні утримання.
- [ ] Локальні агрегати за кварталом/продавцем: суми, кількість діяльностей, комісії/утримання, коригування; drill-down до подій.
- [ ] Повнота профілів, підзвітність, невирішені розбіжності, блокери; пояснення рішення та джерело правила.
- [ ] Незмінний snapshot, джерела й версія правил, погодження, демонстраційний артефакт. Без офіційної XSD не називати XML валідним файлом подання.
- [ ] Симуляція: передано, очікування, технічне отримання, прийнято, відхилено, недоступність. HTTP success не дорівнює прийняттю звіту.
- [ ] Корекція новою версією з причиною, посиланням і новим погодженням; кур'єрський витяг із того самого snapshot.

Приймання: контрольні суми відтворюються; нові події не змінюють поданий snapshot; retry не переводить rejected в accepted самостійно; усі демоартефакти позначені як непридатні для реального подання.

- [ ] Rahunok admin: клієнти, онбординг, інтеграції, черги помилок, технічний журнал, симуляція призупинення. Без постійного доступу до всіх PII; винятковий доступ має причину, строк і аудит.
- [ ] Журнал actor/context/time/result. Локальний demo audit не видається за захищений серверний журнал.
- [x] Маршрут A: пакет демооператора -> уточнення -> реєстрація -> ключ та імпорт -> готовність кур'єрів -> батч -> часткове виконання -> звірка -> звіт -> відмова -> корекція -> прийняття -> витяг кур'єру. Один браузерний контекст без reset; оператор і первинні фінансові записи вже існують у seed, provisioning нового tenant не перевіряється.
- [x] Маршрут B: зовнішні виплати, спільний кур'єр, повтор і конфлікт ID, повернення, відкликаний ключ, заборонений прямий маршрут, reload, reset. Один браузерний контекст; UI після відкликання забороняє імпорт, відмова доменної команди перевіряється ledger unit tests.
- [ ] Desktop 1440 px/mobile 390 px: відсутність перекриття, фокус, клавіатура, назви полів, контраст, підтвердження небезпечних дій.
- [ ] Зафіксувати доступні функції, симуляції, блокери live та результати перевірок. Не додавати вигаданих SLA/сертифікацій.

Демо приймається після обох маршрутів і scoped check/test/build. Попередні 13 тестів є регресійною базою, не доказом покриття нового циклу.

## 11. E9: реальний API та persistence

Цільова архітектура попереднього обговорення: Svelte SPA -> Cloudflare Worker -> Drizzle -> Turso Cloud/libSQL; Supabase Auth для користувачів. Ресурси не створені. Властивості preview-рушія Turso не приписуємо libSQL.

- [ ] Погодити Auth-проєкт (окремий/спільний), dev/live, регіони, бюджет, доступи. Free є цільовим стартом, не гарантією безкоштовної експлуатації.
- [ ] Окремий Worker зі static assets; не змінювати чинні routes/auth. Перевірити актуальні docs і сумісні стабільні версії Drizzle/Worker driver.
- [ ] Control DB: оператори, memberships/delegations, перевірені user links, registry баз. Окрема операційна база на оператора; оператор може мати кілька платформ.
- [ ] JWT verification з довіреним issuer/audience, актуальні memberships; machine credentials окремо. JWT role authenticated не є бізнес-роллю.
- [ ] Вибір бази сервером після перевірки прав, server-only scoped credentials. Drizzle не є авторизацією, Supabase RLS не поширюється на Turso.
- [ ] Версії міграцій усіх operator DB, retryable provisioning і блокування. Не припускати транзакцію між Auth/control DB/operator DB.
- [ ] Замінювати gateway модулями: організації -> заявки/продавці -> ingestion -> виплати -> звіти. Для перенесеного модуля прибрати прямий browser business-table access; неперенесені live-функції недоступні, без fixture fallback.
- [ ] Durable idempotency, транзакційні переходи, конкуренція, outbox/retry. Серверні негативні тести чужих ID, читань, записів, exports, jobs і документів.
- [ ] Приватне сховище документів/артефактів (кандидат R2), metadata у Turso, контроль типу/розміру, перевірка файлів, обмежені завантаження, retention, маскування логів.
- [ ] Фонові імпорти/звіти, ліміти навантаження, метрики. Queues/Workflows обрати за потребою, не додавати всі продукти наперед.
- [ ] Незалежні backup/restore, погоджені RPO/RTO, контрольне відновлення. Після restore зовнішні дії призупинені до звірки. Одноденний PITR не замінює архів фінансових доказів.

Приймання: серверна відмова без прав, ізоляція двох tenant, persistence після restart, міграція двох баз, replay/concurrency tests, recovery rehearsal. Банківський/державний sandbox не змішується з live-доказами.

## 12. E10: невідомі інтеграції та активація

| Невідоме | До підтвердження | Умова live |

Кожний адаптер активується окремо після contract/sandbox tests. Недоступність повертає помилку/очікування, не демоуспіх. Спочатку погоджений тестовий deployment, потім окремий дозвіл на production, подання та банківські дії.

## 13. Правила роботи

1. Один активний E-етап; вибрати малий завершуваний сценарій, зафіксувати залежності.
2. Перед зміною прочитати owning implementation і найближчий тест; зберігати стиль, не рефакторити сусідні продукти.
3. Після першої правки відразу focused validation; потім завершити негативні стани.
4. Для Svelte використовувати MCP/autofixer; нові domain tests додавати поряд із чинними, браузерні інтегрувати з наявним підходом.
5. Gate етапу з кореня: `npm run check:platform`, `npm run test:platform`, `npm run build:platform`, браузерна перевірка шляху. На Windows Vitest використовувати канонічний `D:/` root. Root gate потрібний при зміні root adapter/shared build.
6. Оновити статус і журнал нижче: реалізоване, перевірки, ризики. Наявність екрана не означає завершений процес.
7. Нові питання задавати перед залежним етапом. Відсутність державних ключів не блокує демо; секрети в чаті не запитуються.
8. Commit, provisioning, deployment, реальні платежі й зміни заблокованих процесів не виконуються автоматично.

### Карта ресурсів локального адаптера

Усі операції виконуються через `DemoGateway`, не через мережу. `operatorId` і persona у браузері є демоконтекстом, а не довіреною ідентичністю. Для E9 потрібен окремий серверний контракт.

| Ресурс | Локальні команди / проєкції | Відношення до legacy OpenAPI |
| --- | --- | --- |
| Operator registration | `registration.save/approve/submit/resolve/evidence` | `/operators/register` не описує весь версійований цикл; це не сумісна реалізація endpoint |

| Team / machine credentials | `member.invite/status`, `key.create/rotate/revoke` | Немає повного контракту membership/key lifecycle; live-ключ відхиляється |
| Activity / income / customer payment | `ledger.import`, `integration()`, `view()` | `/events/batch` має інший payload; `/orders/split` не реалізовано як платіжний split |

Повтор не збільшує суми, зміна payload під тим самим ключем відхиляється. Ці обмеження не є production SLA.

### Архітектурний висновок

- Єдині команди й проєкції зв'язують операції, виплати та звіти; UI не записує фінансові суми напряму. Історичний snapshot не змінюється після нових подій.
- Розділено оплату покупця, винагороду, резерв і підтверджену виплату. Погодження відокремлено від виконання; unknown вимагає звірки. Після призупинення дозволені лише відповідні завершення попередніх зовнішніх дій та відкликання доступу.
- Межа безпеки відсутня у браузерному демо: користувач може змінити код/storage/persona. Тести доводять поведінку проєкцій, не захист від зловмисного клієнта.
- Локальний журнал містить застосовані зміни й дозволені читання через support access, не всі читання/відхилені спроби. Немає tamper-proof аудиту, атомарності між вкладками, довгострокового архіву чи доказу доставки повідомлень.
- DEMO-UA-v2 потребує ручної оцінки підзвітності та явних комісій/утримань для готового звіту. Це не податковий рушій або правове рішення. Вимога одночасних Diia/BankID/IBAN-доказів і строк 365 днів є демополітикою, не нормою закону.
- Тимчасовий доступ підтримки реалізовано лише для синтетичних даних: reason, scope, незалежне погодження, строк, read audit і revoke. У live усі ці перевірки та аудит мають виконуватися сервером; показане вже прочитане неможливо відкликати з пам'яті користувача.
- Великий спільний JS-пакет із legacy є ризиком завантаження. Розділення коду, навантаження, доступність і юридична простежуваність потребують окремого приймання; довільне підвищення ліміту Vite не усуває ризик.

## 18. Межі розширеної моделі

- Нові реєстраційні пакети зберігають точні версії документів. Заміна файла потребує нової версії пакета й нового погодження. Структуровані поля доповнюють початкові summary-поля; старі події без details залишаються сумісними, тому це не універсальний валідатор офіційної анкети.
- Документи обмежені синтетичними DEMO TXT: 20 KB на файл, 100 версій на оператора. Остання submitted/rejected/expired версія є блокером відповідної готовності. Відсутність усіх документів не блокує сама собою: обов'язкові категорії ще мають бути юридично визначені.
- Нові gateway-події мають `evidencePolicy: 2`, нові звіти `DEMO-UA-v2`. Історичні події без цих позначок відтворюються за попередньою поведінкою; не застосовуємо нові правила заднім числом.
- Імпорт повертає стабільні per-row correlation ID і processed/replayed/rejected. Зміна payload під існуючим ключем відхиляється; усі суми залишаються цілими копійками.
- Слово «самозайнятий» є терміном інтерфейсу, не автоматичною юридичною кваліфікацією. Внутрішні courierId/kind і початкові seed-ID залишені для сумісності; таксі та послуги не моделюються як лише доставка.
- Погоджений локальний цикл деталізовано та перевірено, але ручний огляд E8 і вимоги законодавства, серверної безпеки й зовнішніх провайдерів не закриті. Не використовувати загальне формулювання «повністю готово» поза цими межами.
